# 基于知识库检索的旅游行程规划系统

> 论文题目定稿（2026-10-23）｜ 系统简称：**智慧旅游规划助手**（AI Tourism）

基于 LangChain 1.x + 通义千问 + Chroma 向量库构建的 **RAG 旅游规划 Agent**。
用户输入目的地、天数、预算、人数与兴趣偏好，Agent 会先检索本地旅游知识库，
再融合真实资料生成结构化的行程方案，并标注引用来源。

支持两种交互方式：命令行（CLI）与 Gradio Web 图形界面。

## ✨ 核心特性

- **RAG 全流程** — 文档切分 → 文本向量化 → 相似度召回 → Prompt 组装 → 来源标注
- **Agent 自主决策** — 由模型判断是否需要检索，可针对行程不同方面多次调用检索工具
- **差异化切片** — Markdown / JSON / 纯文本三类资料采用不同切片策略，保留标题层级
- **四件套方案输出** — 预算条、行李清单、交通方案、日历导出（.ics）
- **多端可用** — CLI、Gradio Web、局域网访问、公网访问（Cloudflare 隧道）、二维码分享海报
- **187 张实景图册** — 按兴趣偏好召回，回填需求表单，弱网环境下也不影响排版

## 一、需求分析

### 1.1 项目背景

通用大模型在旅游规划场景存在两个明显短板：

1. **信息不可信**——门票价格、开放时间、预约政策这类时效性强的数据，模型很容易凭记忆编造，且无法追溯来源。
2. **缺乏本地沉淀**——旅游攻略资料通常以文档形式散落在本地，模型训练数据既不含这些内容，也无法直接读取。

因此本项目采用 **RAG（检索增强生成）+ Agent** 架构：把本地旅游攻略、景点数据向量化入库，
由 Agent 在回答前主动检索，做到「有据可依、来源可查」。

### 1.2 核心需求

| 功能模块 | 需求描述 |
|---------|---------|
| 多格式知识库 | 支持 Markdown 攻略、结构化 JSON、纯文本三种资料共存 |
| 差异化切片 | 按文档类型选择切片策略，保留标题层级等结构信息 |
| 向量检索 | 通义千问 text-embedding-v3 向量化，Chroma 持久化，Top-K 相似检索 |
| Agent 决策 | Agent 自主判断是否需要检索，可针对不同方面多次调用检索工具 |
| 行程生成 | 输出每日行程、预算估算、美食推荐、住宿建议、出行注意事项五段式方案 |
| 来源标注 | 引用知识库时标注来源文件与标题层级，未命中时明确标注「通用参考」 |
| 实景图册 | 34 个省级行政区共 187 张实景图，**每区 6 类兴趣偏好（自然风光/历史文化/美食探店/购物娱乐/亲子游/户外探险）各至少 1 张**；生成方案后按目的地展示，并按用户勾选的偏好优先排序（图文解耦，不污染检索） |
| 待机图带 | 页面右栏顶部首屏即见的横向流动实景图带，缓慢左移、无缝循环，点击图片直接把目的地填进表单 |
| 双端交互 | 命令行界面（可观察 Agent 思考轨迹）与 Gradio Web 界面 |

### 3.3 RAG 数据流

```
【构建阶段】一次性执行
  knowledge_base/ 原始资料
        ↓  document_loader.batch_load_tourism_docs()
   原始 Document（含 source 元数据）
        ↓  text_splitter（按 md / txt|json 分流）
   切片 Document（md 保留 Header 1/2/3）
        ↓  OpenAIEmbeddings(text-embedding-v3)
   向量  →  写入 chroma_db/（collection: tourism_kb）

【查询阶段】每次对话
  用户问题
        ↓  Agent 判断需要专业资料
  travel_knowledge_search_tool.invoke(query)
        ↓  retriever.invoke(query)  →  Top-5 相似片段
  「[参考1] 成都旅游攻略.md（… > 住宿建议）」+ 正文
        ↓  回灌给 LLM
  结构化方案 + 📚 参考资料标注
```

### 3.4 三类资料的切片策略

| 资料类型 | 示例文件 | 切片方式 | 切片单位 | 保留的元数据 |
|---------|---------|---------|---------|-------------|
| Markdown 攻略 | `成都旅游攻略.md` | `MarkdownHeaderTextSplitter` | 最小标题段落 | `Header 1/2/3`、`source` |
| 结构化 JSON | `景点数据.json` | `JSONLoader` 思路，逐条 JSON 序列化 | 一个景点一条 | `source` |
| 纯文本 | `出行贴士.txt` | `RecursiveCharacterTextSplitter` | 500 字符 / 重叠 80 | `source` |

**关键参数说明**：

- Markdown 切片设置 `strip_headers=False`。若使用默认的 `strip_headers=True`，标题会被
  从正文中剥离只留在 metadata 里，导致片段变成「门票 55 元」这样失去主语的孤立文本，
  向量化后语义不完整、检索命中率明显下降。
- 纯文本 `chunk_size=500`、`chunk_overlap=80`。旅游资料信息密度低于说明书类文档，
  片段过短会割裂上下文，故取较大的窗口。
- 加载器使用 `os.walk` **递归扫描**子目录。34 个目的地按行政区类别分目录存放
  （`destinations/省/`、`destinations/直辖市/` 等），若沿用只扫一层的 `os.listdir`，
  子目录中的资料会被全部漏掉。

### 4.2 关键技术实现

**① LangChain 0.x → 1.x 的 API 迁移**

项目原始代码沿用了 0.x 写法，在本机 1.x 环境下无法运行，主要改动：

| 旧写法（0.x） | 新写法（1.x） | 原因 |
|--------------|--------------|------|
| `from langchain_community.vectorstores import Chroma` | `from langchain_chroma import Chroma` | 集成包拆分 |
| `retriever.get_relevant_documents(q)` | `retriever.invoke(q)` | 统一 Runnable 接口 |
| 普通函数直接作为工具 | `@tool` 装饰器 + 类型注解 + docstring | 1.x 要求 StructuredTool |

**② 检索器懒加载 + 并发安全**

`tools/travel_tools.py` 中检索器采用「懒加载 + 双重检查锁 + 失败标记」：

- 首次调用工具时才加载向量库，避免「知识库未构建」导致程序在 import 阶段就崩溃；
- 加载失败时工具返回明确提示，Agent 可据此降级为通用知识作答，而不是直接抛异常；
- 失败后置位 `_RETRIEVER_FAILED`，避免每次对话都重复尝试加载、拖慢响应；
- **必须加线程锁**：LangGraph 会**并行**执行同一批工具调用（例如同时检索门票、美食、住宿），
  多个线程同时初始化 Chroma 客户端会互相抢占资源，导致部分调用抛异常并把失败标记置真，
  表现为「知识库明明已构建，却提示加载失败」。加锁后初始化只执行一次（快路径无锁，检索仍可并发）。

**③ 元数据合并而非覆盖**

Markdown 切片后必须用字典展开合并：

```python
split.metadata = {**doc.metadata, **split.metadata}
```

若写成 `split.metadata = doc.metadata`，`MarkdownHeaderTextSplitter` 产出的
`Header 1/2/3` 层级信息会被整个覆盖掉，检索结果将无法追溯章节。

**④ 引导 Agent 并行检索**

单次检索很难同时覆盖门票、交通、美食、住宿等多个方面。系统提示词中明确要求
一次性**并行**发起 2~3 个不同角度的检索（而不是一轮一轮串行追加），
既保证信息完整、避免模型在检索结果不完整时凭记忆补全价格与时刻，也不额外拖慢响应。

**⑤ 流式输出与响应速度优化**

方案生成采用 Agent 的 messages 流模式，把「等全部生成完」拆成两段可见进度：
检索阶段只推送进度提示（不推送模型寒暄，避免「说一句话就干等半分钟」的观感），
检索一结束就逐段输出正文；服务启动时还会在后台线程预热向量库。

界面提供三档「方案详略」，档位同时决定**模型**与**提示词的篇幅策略**：

| 档位 | 模型 | 篇幅策略 | 实测字数 | 正文首字 | 全部完成 |
|---|---|---|---|---|---|
| ⚡ 快速 | qwen3.6-flash | ≤ 700 字 | 1191 字* | 2.1s | 4.4s |
| ⚖️ 均衡（默认） | qwen-plus | ≤ 1000 字 | 1515 字 | 3.1s | 10.3s |
| 📖 详细 | qwen-plus | ≤ 3000 字 | 4670 字 | 3.5s | 46.6s |

*快速档原为 qwen-turbo（该实测数据在其上测得）；因百炼 2026-10-10 下线旧主线模型
（公告 118177），已迁移至官方推荐的 qwen3.6-flash，迁移后实测表现见下方验证记录。

> 作为对照：优化前只有「详细」这一种效果，且必须等 **45.8 秒**才显示第一个字；

### 7.2 Gradio Web 方式

浏览器打开 `http://127.0.0.1:7860`，填写表单：

| 字段 | 示例值 |

| 目的地 | 成都 |

表单里的**方案详略**决定生成速度与详细程度：⚡ 快速（约 5 秒，最精简）、
⚖️ 均衡（约 10 秒，默认）、📖 详细（约 45 秒，内容最全）。

点击「生成旅游方案」，页面会**边生成边显示**方案（先给检索进度提示，约 3 秒后正文
逐段出现），末尾附上本次命中的知识库来源清单，
并在方案下方自动展示该目的地的实景图册（输入「成都」会展示四川图册，
输入「洪崖洞」会展示重庆图册）。图注标注了每张图对应的兴趣标签，
图册按你勾选的兴趣偏好优先排序。

> **往返路费卡（出发地选填）**：填了「出发地」后，方案正上方会出现一张彩色提示卡，
> 把「出发地 → 目的地」的往返路费摆到最醒目的位置——填完出发地 + 目的地 + 预算的
> 一瞬间就会显示，不必等生成。
> **交通方式由用户自己选**：卡片上方有单选项「🚉 交通方式（路费按哪种核算）」，
> 可在 🚄 高铁二等座 / 🚂 普速硬卧 之间切换，预算按所选方式即时重算；
> ✈️ **机票只展示、不可选**——同一航线淡旺季能差一倍以上，卡片里给区间并明确标
> 「仅参考 · 不可选」，不参与预算核算（这是刻意设计，避免拿一个随机折扣去扣预算）。
> 卡片里**三种方式都列出来**（价格区间 + 往返耗时），当前核算的那种高亮打标
> 「✅ 本次核算」，谁在参与扣减一目了然。
> 预算判定分三态，左侧色条一眼可辨：
> 🟩 **预算够**（绿）：路费已从人均预算里扣掉，写明扣完还剩多少、每天能花多少；
> 🟨 **偏紧**（橙）：路费装得下，但目的地部分要压缩，并给出「建议预算提到多少」；
> 🟥 **不够**（红）：路费本身就超出预算，明确提示「这笔钱要单独准备」，
> 并按出行人数算出要另外准备的总额。
> 估算不接外部接口（离线可跑、票价波动大），走「城市坐标 → 大圆距离 → 铁路里程
> （×1.27 绕行系数）→ 分方式单价」的链条：高铁约 0.42 元/km、普速硬卧约 0.23 元/km、
> 机票按里程给区间，全部标注「约」与「以购票平台为准」。识别不了的（如「火星」）
> 会明确说「没能识别」，绝不瞎算；出发地留空则整张卡不出现，原有体验不变。
> 特殊线路另有处理：海南无跨海高铁、拉萨只有青藏铁路普速——这两种情况单选项
> 只剩一种，卡片注明「无高铁」并给出跨海/进藏提示；台湾只能飞机，卡片按机票估算
> 并注明「仅供预算参考」。
> 同时该结论会写进给模型的提问（`core/prompts.py` 第 9 条规则）：写明用户所选方式、
> 要求模型按同一口径说话、不得擅自改按机票重算——避免模型口径与页面卡片打架。
> 核心算法在 `core/transport.py`，可直接 `python -m core.transport` 自测。

> **预算去向条**：方案生成完，正文下方会出现一条「💰 预算去向（人均）」堆叠条——
> 往返路费 / 门票 / 当地交通 / 住宿 / 餐饮各占多少一眼看清（纯 CSS，无图表库依赖）。
> 路费段来自系统估算，其余各项**从方案正文的预算小节里解析**（住宿按晚数、餐饮按天数
> 折算成总额）；解析不出足够分项时整条隐藏，宁可不出图也不瞎画。若分项合计超出人均
> 预算，会给出「超出约 X 元」的提示；有剩余则把剩余也画成一段。

> **行李清单**：填上目的地就**即时**出现（不等生成），按「人手必备 / 目的地特别提醒 /
> 按你的兴趣」三组展示。纯规则生成（`core/packing.py`，不调模型）：气候按纬度 + 当前
> 月份判断，海滩城市加泳衣防晒、高原城市加抗高反与防晒、冬季北方加羽绒服雪地靴；
> 衣物数量按天数给（天数 +1 套、封顶 7 套）；兴趣偏好追加对应装备。规则型生成对这种
> 清单任务比 AI 更合适——秒出、稳定、可解释。可直接 `python -m core.packing` 自测。

> **弹性保障卡（行程留活口）**：行李清单下方还有一张紫色「🛡 弹性保障」卡，与行李清单
> 同源即时刷新，回答「行程排死了怎么办」，由 `core/flexible.py` 纯规则生成：
> - **🌦 可能被迫改行程的天气**——按「目的地气候规律 + 当月」给风险提示（6~10 月沿海
>   提台风并建议留缓冲、5~10 月西南提雨季建议户外排上午、7~8 月火炉城市建议午后进室内、
>   高原全年提示天气变脸快……），红/橙/灰标注等级；明确注明**是气候规律不是实时预报**。
> - **🕐 每天留多少机动**——按天数给基础值（1~2 天 60 分钟 → 8 天以上 150 分钟），
>   含户外/亲子/探店等兴趣再加码（封顶 180 分钟），并写明依据。
> - **🔀 赶不上计划的舍弃顺序**——先舍顺路打卡点、再舍排队型项目、已预约已购票的必须
>   保住、核心地标只做减法；连续两天都要砍说明整体排太满。
> - **☔ 雨天室内替代**——按兴趣给类型（自然风光→地质馆/温室，亲子→科技馆……），
>   兴趣项最多占 4 条，通用的「博物馆/商场」永远保留。
> - **✅ 出发前确认**——离线包、客服电话，并按风险动态追加（台风季→可免费取消的
>   机票住宿、高原→抗高反药品、长线→留一个空白天）。
>
> 弹性不只在这张卡上，**方案正文本身也被要求留活口**（`core/prompts.py` 规则 10 +
> `build_query` 里的硬性要求）：模型必须给每天写 `🕐 机动` 时段、重点项目带 `☔ 备选`、
> 末尾必须有 `🛡 弹性保障` 小节（舍弃顺序 + 天气应变 + 出发前确认）。实测 balanced 档
> 最初会为守字数砍掉该小节，在用户消息里钉一条硬性要求后稳定输出。导出文件的信息头里
> 也带一行弹性摘要。可直接 `python -m core.flexible` 自测。

> **方案导出与历史**：方案下方有「⬇️ 下载 Markdown」「⬇️ 下载 Word 文档」两个按钮，
> 导出文件自带信息头（目的地 / 出发地 / 路费与弹性摘要 / 生成时间）；Word 走 HTML 版 .doc
> （WPS 与 Word 直接打开，零额外依赖）。左栏「🕘 历史方案」保留最近 5 份，下拉即可
> 回看对比（存服务器内存，重启即清空）。生成收尾统一挂在 `submit_btn.click(...).then(...)`
> 的 `after_generate` 里，主流程 `travel_planner` 的输出签名不因这些功能变长。

打开页面，**右栏顶部**就是一条**横向流动的全国实景图带**（首屏即见，不必滚动）：**34 个行政区各出 1 张**
（随机顺序），以纯 CSS 匀速从右向左缓慢移动（走完一圈约 260 秒）、无缝循环，
没有「整批换图」的跳变；**点击任意图片会直接把目的地填进表单**。
转一圈就能看到全国所有省区，不必靠运气等某个区出现。

> **顺序随机是怎么做的**：每次打开页面，前端会对两份卡片做一次**同一排列**的
> Fisher-Yates 洗牌（只重排已有 DOM，不多传一个字节，比服务端随机省下每次刷新的
> 整条图带流量）。之所以强调「同一排列」——两份必须是同样的顺序，否则
> `translateX(-50%)` 的接缝两侧会是不同卡片，循环时会看出跳变。

> **点选回填的防竞态设计**：行政区不依赖任何会被刷新的缓存索引，而是**从卡片自带的
> `data-region` 属性（`省份 · 景点` 解析而来）里直接读出**，
> 再拿 34 个行政区白名单校验；认不出来时**什么都不填**，宁可不动也不填错。
> 图带是纯 CSS 动画、没有定时器，不存在「点下去的一瞬间图刚好换了」的问题。

> **无缝滚动的实现要点（实测踩坑）**：把同一批卡片复制两份首尾相接、动画从
> `translateX(0)` 走到 `translateX(-50%)`，视觉上就会永远流动。但 `translateX(-50%)`
> 的百分比是**相对轨道自身宽度**算的，所以「轨道宽度的一半」必须**恰好等于一份卡片的宽度**：
> 若把两份卡片直接摊在同一个带 `gap` 的 flex 里，两半之间会多出一个 gap，接缝处每循环一次
> 就跳 5~10px；若允许 `flex-wrap: wrap`，卡片会折成多行、高度暴涨（实测 2115px，几乎全被
> 容器裁掉）。因此轨道必须 `flex-wrap: nowrap` + `width: max-content` + 组间 `gap: 0`，
> 间距只放在组内（组尾用 `padding-right` 补齐）。实测（Chrome 153，34 张 190px 卡）：
> 轨道 13600px、单组 6800px、误差 **0.00px**，首尾完全衔接、没有空节。
> 图片以 base64 内嵌进隐藏的 `<symbol>` 库，副本用 `<use>` 引用，34 张实际只存 34 份数据。
>
> **体积控制：图带专用缩略图**。图带上单张只显示 190px 宽，内嵌 1000px 原图
> （平均 126KB）纯属浪费——`_image_data_uri` 会先把图等比压到 380px 宽、JPEG q78 再内嵌，
> 单张降到约 30KB。34 张全上的主页约 3.6MB、/config 约 3.4MB；若不压缩直接内嵌原图，
> 仅 base64 就 4.2MB/份，传输量翻倍还不止。压缩结果按（路径, 宽度, 质量）缓存，重建图带不再重复解码。
>
> **⚠️ 图带点击回填的正确写法（两个 P0 血泪坑）**：
> ① **js_on_load 的作用域里没有 Python 变量名。** Gradio 前端执行它的方式是
> `new Function("element","trigger","props","server","upload","watch", code)`，
> 只有这 7 个参数。写成 `strip_out.select(region)`（Python 变量名）会抛
> `ReferenceError`，且抛在 click 回调内部——绑定照常、渲染照常、页面无提示，
> 唯一症状就是「点了没反应」（2026-09-22 线上事故）。官方唯一姿势是
> `trigger('select', {region: ...})`，Python 侧用 `evt: gr.EventData` 接
> （`evt.region` 取值）。
> ② **不要写 `inputs=[strip_out]`。** 那会把图带组件的当前值（约 3.9MB HTML）
> 当参数回传服务端；inputs 留空后数据走事件数据，请求体只有几十字节。
> 仍须 `api_visibility="undocumented"`：否则该端点进「Use via API」文档，
> 大段内容被复制若干份（实测主页曾因此 3.2MB → 20.2MB）。
> 验收红线：「端点在 config 里存在」≠「前端能调通」，必须真浏览器点一次、
> 读回填值（Gradio 6 不生成 component-N 容器 id，定位输入框用 placeholder）。

> **页首横幅（2026-09-22 界面美化）**：页首原来两行素 Markdown 换成渐变横幅卡
> （浅蓝→浅青渐变底、圆角描边），标题下一句话说明 + 五枚能力徽章
> （🗺 覆盖 34 个省级行政区 / 🖼 187 张实景图 / 💸 路费预算即时核算 /
> 🛡 行程弹性保障 / 🎒 行李清单自动生成）。徽章数字直接从图册索引统计
> （`_hero_html()`），以后增删图片无需改文案。手机端有独立的紧凑样式。

> **「没想好去哪儿」直达面板（右栏空白补位）**：待机状态下右栏只有图带和两个
> 下载按钮，下面一大片空白——现在由一块绿色「🎲 没想好去哪儿？点一下直达」面板
> 补位：12 个热门目的地芯片（四川/北京/陕西/重庆/海南/云南/湖南/江苏/浙江/山西/
> 甘肃/西藏，各带一句看点），**点击任意芯片直接把目的地填进表单**，与图带共用
> 同一条事件通道（前端 `trigger('select', {region})` → 服务端同一个 `show_pick_hint`，
> 白名单校验只有一份）。面板常驻右栏底部：待机时正好补住空白；生成方案后排在
> 最尾（图册之后），不抢正文位置。图册索引里没有的区不上芯片，避免点了没反应。

> **手机版图册不再截断（响应式修复）**：`gr.Gallery(height=640)` 是「固定 640px 高 +
> 内部滚动条」，手机上之前只在 CSS 里把滚动区压到 58vh，组件外框仍占 640px——
> 实机表现为「最后一排被拦腰截断 + 组件下方一大片留白」。现在给图册加了
> `elem_id="dest-gallery"`，手机端（≤640px）把整册改成高度自适应：
> 外框 `height:auto`、滚动区 `max-height:none + overflow:visible`、行高交给内容
> （`grid-template-rows:none`，缩略图按 aspect-ratio 定方格）。实测 390×844 视口：
> 6 张图 2 列 × 3 行全部完整展开（每格 151px），`scrollHeight == clientHeight`
> （无内部滚动），整页自然下滚。桌面端仍保持 640px 固定高 3 列不变。

### 7.3 公网 / 手机访问

#### 7.3.1 常驻公网链接（推荐）

项目已托管到云端，**网址固定不变、不依赖本机开机**，手机流量、异地电脑随时可打开：

```
https://smart-travel-planner.app.workbuddy.host/
```

访问账号 `travel`、密码 `travel2026`。云端由 `server.py` 作为入口启动
（读取平台注入的 `PORT` 环境变量、监听 `0.0.0.0`），源码、`chroma_db/` 向量库
与 `assets/` 图册一并随发布包上传，因此云端同样具备完整的 RAG 检索与实景图能力。

需要更新线上内容时，改完本地代码重新发布一次即可，**链接保持不变**。

> **踩坑记录：登录后停在登录页、点了登录没反应**
>
> 托管网关转发时会改写 `Host` 头，Gradio 据此推断出的「公开地址」会变成平台内部的
> 沙箱域名（形如 `https://7860-xxxx.e2b.bj7.sandbox.cloudstudio.club`）。登录页的前端
> 脚本以这个地址为 API 基址，于是 `POST /login` 发到了内网域名，登录 cookie 也就落在
> 那个域下，用户回到真实域名刷新仍是登录页。生成方案时的 `predict` 请求同理。
>
> **修法**：入口用 `launch(root_path="https://完整公网地址")` 显式指定公开地址，
> Gradio 会原样采用（官方支持传完整 URL）。`server.py` 已按此处理，域名可用环境变量
> `TRAVEL_PUBLIC_URL` 覆盖。账号密码、静态资源路径不受影响。
>
> 自检（输出的应是公网域名，而不是含 `sandbox.cloudstudio.club` 的内网地址）：
>
> ```bash
> curl -s https://smart-travel-planner.app.workbuddy.host/ | grep -o '"root":"[^"]*"'
> ```

#### 7.3.2 临时隧道（本机对外，备选）

如果只想临时演示、且希望走自己这台机器的算力，用公网启动器：

```bash
python tools/start_public.py
```

脚本会在本机起服务的同时，用 Cloudflare 建立一条临时隧道，并在窗口里用醒目
方框打印形如 `https://xxx.trycloudflare.com` 的公网地址。手机浏览器打开该地址，
先进入 Gradio 登录页，输入账号 `travel`、密码 `travel2026` 即可使用。

全部启动方式的可访问范围：

| 启动方式 | 命令 | 可访问范围 |
|---------|------|-----------|
| 默认 | `python app_gradio.py` | 仅本机（127.0.0.1） |
| 局域网 | `python app_gradio.py --lan` | 同一 Wi-Fi 下的手机 / 电脑 |
| 常驻公网 | 云端已发布链接（见 7.3.1） | 任意网络，地址固定、无需开机 |
| 临时公网 | `python tools/start_public.py` | 任意网络，但地址每次变、需本机开机 |

使用注意：

- 云端链接地址固定，但每次改完代码需要重新发布才会生效；
- 临时隧道的地址由 Cloudflare 免费随机分配，**每次启动都不同**，关闭窗口立即失效；
- 两种公网方式都强制开启登录（链接是公开的，任何人拿到都能消耗模型 API 额度）；
  想换密码设环境变量 `TRAVEL_PWD`（同理 `TRAVEL_PORT` 可换端口）；
- 临时隧道依赖 `tools/cloudflared.exe`（约 52 MB，Cloudflare 官方工具，已随项目提供）；
- 临时隧道无可用性保证，长时间空闲可能被回收，重启脚本即可获得新地址。

### 7.4 推荐演示用例

1. **验证 RAG 生效**——输入「故宫门票多少钱，需要提前预约吗」，观察轨迹中是否调用了检索工具，
   以及答案中的价格（旺季 60 元 / 淡季 40 元）是否与知识库一致。
2. **验证多轮上下文**——先问「成都有哪些必去的景点」，再追问「那住哪儿比较方便」。
3. **验证图文联动**——输入「重庆 3 天怎么玩」，方案下方应自动出现该目的地实景图册
   （洪崖洞 / 解放碑 / 李子坝轻轨穿楼 / 火锅 / 山城步道等 6 张，覆盖 6 类兴趣）。
4. **验证兴趣排序**——同样输入「拉萨 3 天」，勾选「美食探店」时图册首图应为藏式甜茶等美食图；
   改勾「自然风光」时首图应换成纳木错等风光图。
5. **验证知识库边界**——问一个知识库没有的境外目的地（如「巴黎 3 天怎么玩」），
   答案应标注「【通用参考】」，且不展示图册（回到横向流动的待机图带）。

## 八、常见问题

**Q1：提示「未找到已构建的向量库」**
先运行 `python init_kb.py`。向量库是本地文件，不随代码一起分发。

**Q2：检索不到内容，或答非所问**
检查 `knowledge_base/` 目录下是否有资料文件（支持子目录，加载器会递归扫描），
然后重新运行 `python init_kb.py` 重建。可用 `python tools/check_kb.py` 定位问题。

**Q3：`ModuleNotFoundError: No module named 'langchain_chroma'`**
依赖未装全，执行 `pip install -r requirements.txt`。

**Q4：门票价格与实际情况不符**
知识库中的价格可能已过期。直接修改 `knowledge_base/` 下对应的资料文件，
再重新运行 `python init_kb.py` 即可。

**Q5：想扩充新的目的地**
在 `knowledge_base/destinations/{类别}/` 下新建三个文件：
`{省级行政区}-主攻略.md`、`{省级行政区}-路线库.md`、`{省级行政区}-预算人数适配.md`，
按 `doc/知识库设计说明.md` 的模板组织内容（章节标题是切片依据，不可随意改动），然后重建向量库。
